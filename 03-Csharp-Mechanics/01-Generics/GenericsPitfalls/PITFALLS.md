## Модель предметної області (коротко)

```text
IEntity { Id }
  ├── Animal { Name, OwnerId : int? }
  │     ├── Dog { Breed }
  │     └── Cat { IsIndoor }
  └── Owner { Name, Pets : List<Animal> }   + IEquatable<Owner>

IReadOnlyRepository<out T>   — тільки віддає T
  └── IRepository<T>         — ще й приймає T (Add, Remove)
        └── InMemoryRepository<T> where T : class, IEntity

IValidator<in T>             — тільки приймає T
  ├── AnimalValidator : IValidator<Animal>
  └── DogValidator    : IValidator<Dog>
```

Кожен `Dog` — це `Animal`, але **`List<Dog>` — не `List<Animal>`**, а
`IRepository<Dog>` — не `IRepository<Animal>`. Майже всі помилки з variance
(пункти 1, 10, 16–18) з'являються саме тому, що інтуїція «собаки — це тварини»
не переноситься автоматично на **контейнери** собак.

# Частина A. Помилки часу виконання

Код збирається без помилок, але під час роботи падає або дає хибний результат.
Такі помилки небезпечніші за помилки компіляції: їх знаходять не програмісти, а
користувачі.

---

## 1. Коваріантність масивів

**Симптом:** `ArrayTypeMismatchException`

```csharp
Animal[] animals = new Dog[2];                 // компілятор дозволяє
animals[0] = new Dog { Name = "Рекс" };        // ок
animals[1] = new Cat { Name = "Мурка" };       // 💥 ArrayTypeMismatchException
```

### Чому так

Масиви посилальних типів у .NET **коваріантні** з першої версії платформи (тоді ще не було
generics). Це означає, що `Dog[]` неявно приводиться до `Animal[]`.

Проблема в тому, що змінна `animals` має **статичний** тип `Animal[]`, а сам об'єкт — це
`Dog[]`. Компілятор бачить лише статичний тип і дозволяє покласти `Cat`
(адже `Cat` — це `Animal`). Тому **під час кожного запису** в масив посилальних типів середовище
виконання перевіряє: «чи справжній тип елемента масиву підходить для цього значення?».
Не підходить — виняток.

Побічний ефект: ця перевірка коштує процесорного часу при кожному записі.

### Що важливо знати

- Масиви **значущих** типів коваріантними не є: `int[]` не можна присвоїти `object[]`.
- **Читання** з такого масиву безпечне. Небезпечний тільки запис.

### Як виправити

Використовувати `List<T>`. Він **інваріантний**: `List<Dog>` неможливо присвоїти
`List<Animal>`, тому підміни немає (див. [пункт 10](#10-listdog--listanimal)).

```csharp
List<Animal> list = new List<Animal>();
list.Add(new Dog { Name = "Рекс" });
list.Add(new Cat { Name = "Мурка" });          // ок: у списку тварин можуть бути й ті, й ті
```

> **Висновок.** Коваріантність масивів — історична помилка дизайну. Generics зроблені
> суворіше саме через неї.

## 2. `ArrayList` замість `List<T>`

**Симптом:** `InvalidCastException`

```csharp
ArrayList pets = new ArrayList();
pets.Add(new Dog { Name = "Рекс" });
pets.Add("Мурка");                             // рядок замість тварини — компілятор мовчить

foreach (object item in pets)
{
    Dog dog = (Dog)item;                       // 💥 на другому елементі: рядок не Dog
}
```

### Чому так

`ArrayList` з'явився до generics. Він зберігає елементи як `object`, тому приймає
**що завгодно**, а повертає теж `object`. Програміст мусить вручну приводити тип
(`(Dog)item`), і **вся відповідальність за правильність лягає на нього**. Компілятор
помилки не бачить, вона проявляється лише під час виконання.

Додаткові витрати: для значущих типів (`int`, `struct`) кожне додавання — це
[boxing](#3-boxing-та-unboxing), тобто виділення пам'яті в купі.

### Як виправити

```csharp
List<Dog> dogs = new List<Dog>();
dogs.Add(new Dog { Name = "Рекс" });
// dogs.Add("Мурка");   // CS1503: cannot convert from 'string' to 'Dog'  — ще на компіляції

foreach (Dog dog in dogs)                      // приведення типів не потрібне
    Console.WriteLine(dog.Name);
```

> **Висновок.** Це головна причина існування generics: перенести перевірку типів
> з часу виконання на час компіляції. `ArrayList` у новому коді не використовують.

## 3. Boxing та unboxing

**Симптом:** `InvalidCastException` при розпакуванні

```csharp
object boxedId = 5;                            // boxing: int → object
long id = (long)boxedId;                       // 💥 InvalidCastException
```

### Чому так

**Boxing** — упакування значущого типу в об'єкт у купі. **Unboxing** — розпакування назад.
Правило суворе: розпакувати можна **тільки в той самий тип**, який упаковували. Всередині
`boxedId` лежить саме `int`, і вимагати з нього `long` не можна — хоча `int → long`
перетворюється неявно, коли змінна має статичний тип `int`. Між упакованим `int` і `long`
немає жодного зв'язку.

### Як виправити

```csharp
long id = (long)(int)boxedId;                  // спершу розпакувати як int, потім розширити
```

або взагалі не пакувати — використовувати `List<int>`, `Dictionary<int, T>`,
узагальнені методи. Generics **не пакують** значущі типи.

### Ціна boxing

- виділення пам'яті в купі для кожного значення;
- тиск на збирач сміття;
- додаткові перевірки типу при розпакуванні.

> **Висновок.** Кожен `object` там, де можна було б `T`, — це і ризик винятку, і зайві витрати.

## 4. `default(T)` = null

**Симптом:** `NullReferenceException`

```csharp
public T? FindById(int id)
{
    return _items.TryGetValue(id, out T? found) ? found : default;   // для class default = null
}

Dog? missing = repo.FindById(42);
Console.WriteLine(missing!.Name);              // 💥 NullReferenceException
```

### Чому так

`default(T)` залежить від того, чим виявиться `T`:

| Тип `T`                 | `default(T)`        |
|-------------------------|---------------------|
| посилальний (`class`)   | `null`              |
| числовий (`int`)        | `0`                 |
| `bool`                  | `false`             |
| `struct`                | усі поля «нульові»  |

Метод «знайти» має чесно повідомити «нічого не знайдено». Для `class` це `null`, і
**викликач зобов'язаний його перевірити**. Оператор `!` (`missing!.Name`) не перевіряє
нічого: він лише вимикає попередження компілятора, тобто програміст каже «повір, тут не null».
Тут він неправий.

Тому в репозиторії тип оголошено як `T?`, а обмеження `where T : class` робить це `?`
однозначним: «посилання, яке може бути null». Компілятор попередить про
розіменування без перевірки (CS8602).

### Як виправити

```csharp
Dog? dog = repo.FindById(42);

if (dog is null)                               // явна перевірка
    Console.WriteLine("Не знайдено");

Console.WriteLine(dog?.Name ?? "(такої тварини немає)");    // ?. та ??
```

### Проблема `default` для значущих типів

Для `struct` «не знайдено» не відрізнити від «знайдено нульове значення»: `default(int)` —
це `0`, а `0` може бути й реальним значенням. Тому для універсального коду частіше
використовують шаблон `TryXxx(out T value)`, що повертає `bool` (як `TryGetValue`).

> **Висновок.** Не ігноруйте попередження про null. Оператор `!` — це обіцянка, а не перевірка.

## 5. `Nullable<T>` і `.Value`

**Симптом:** `InvalidOperationException: Nullable object must have a value.`

```csharp
Dog stray = new Dog { Name = "Бобік" };        // OwnerId не задано → null
int ownerId = stray.OwnerId.Value;             // 💥 InvalidOperationException
```

### Чому так

`int?` — це запис-скорочення для **узагальненої структури** `Nullable<int>`. Вона
складається з двох полів: значення та прапорця `HasValue`. Коли `HasValue == false`,
звернення до `.Value` кидає виняток. Те саме станеться при явному приведенні `(int)stray.OwnerId`.

Компілятор бачить небезпеку і попереджає (CS8629). У демо попередження вимкнено директивою
`#pragma warning disable CS8629` — навмисно.

### Як виправити

```csharp
if (stray.OwnerId.HasValue)                    // або: if (stray.OwnerId is int id)
    Console.WriteLine(stray.OwnerId.Value);

int id2 = stray.OwnerId ?? -1;                 // значення за замовчуванням
int id3 = stray.OwnerId.GetValueOrDefault();   // 0, якщо null
```

> **Висновок.** `Nullable<T>` — приклад того, що generics працюють і для значущих типів.
> `.Value` без перевірки `HasValue` — це той самий клас помилок, що й null-референс.

## 6. Статичні поля в generic-класі

**Симптом:** немає винятку — результат просто **не той, що очікували**.

```csharp
public class EntityCounter<T> : EntityCounterBase
{
    public static int Count;
    public EntityCounter() { Count++; Total++; }
}

new EntityCounter<Dog>();
new EntityCounter<Dog>();
new EntityCounter<Cat>();

EntityCounter<Dog>.Count      // 2
EntityCounter<Cat>.Count      // 1
EntityCounter<Animal>.Count   // 0  ← а не 3!
```

### Чому так

`EntityCounter<T>` — це **відкритий** тип, шаблон. Конкретні типи `EntityCounter<Dog>`,
`EntityCounter<Cat>`, `EntityCounter<Animal>` — **закриті** типи, і кожен із них
є повністю окремим типом. Так само, як у різних класів різні статичні поля, у кожного
закритого типу своя копія `Count` (і свій статичний конструктор).

Спадкування від `Dog` до `Animal` тут не допомагає: `EntityCounter<Dog>` —
не нащадок `EntityCounter<Animal>`, це просто два різні типи.

### Як виправити

Спільний стан кладуть у **неузагальнений** базовий клас:

```csharp
public class EntityCounterBase { public static int Total; }   // одне поле на всю програму
```

`EntityCounterBase.Total` після тих самих трьох створень дорівнює `3`.

### Коли така поведінка — перевага

Окремий стан на кожен `T` бувають потрібним свідомо. Наприклад, кеш, який створюється
один раз для кожного типу: `EqualityComparer<T>.Default`, `Comparer<T>.Default`.
Проблема виникає тільки коли програміст **очікує спільний** лічильник.

> **Висновок.** Тип `Foo<A>` і `Foo<B>` — різні типи. Статика в них не спільна.

## 7. `Dictionary`: дублікат і відсутній ключ

**Симптоми:** `ArgumentException`, `KeyNotFoundException`

```csharp
var owners = new Dictionary<int, Owner>();
owners.Add(1, new Owner { Id = 1, Name = "Олена" });

owners.Add(1, new Owner { Id = 1, Name = "Ігор" });   // 💥 ArgumentException
Owner o = owners[99];                                  // 💥 KeyNotFoundException
```

### Чому так

| Операція                         | Ключ є                     | Ключа немає                   |
|----------------------------------|----------------------------|-------------------------------|
| `dict.Add(k, v)`                 | 💥 `ArgumentException`     | додає                         |
| `dict[k]` (читання)              | повертає значення          | 💥 `KeyNotFoundException`     |
| `dict[k] = v` (запис)            | **мовчки перезаписує**     | додає                         |
| `dict.TryAdd(k, v)`              | `false`, не змінює         | `true`, додає                 |
| `dict.TryGetValue(k, out v)`     | `true`, дає значення       | `false`                       |

Зверніть увагу: **`dict[k] = v` не кидає виняток** — він тихо затирає старе значення. Це
може бути так само небажано, як і виняток, але помітити його важче.
Саме так працює `InMemoryRepository.Add`: `_items[entity.Id] = entity`.

### Як виправити

```csharp
bool added = owners.TryAdd(1, new Owner { Id = 1, Name = "Ігор" });   // false, старий лишився

if (owners.TryGetValue(99, out Owner? found))
    Console.WriteLine(found.Name);
else
    Console.WriteLine("Ключа 99 немає");
```

`TryGetValue` шукає ключ **один раз**. Зв'язка `ContainsKey` + індексатор шукала б двічі.

> **Висновок.** Якщо ключа може не бути — це не виняткова ситуація, а звичайна;
> використовуйте `Try…`.

## 8. Зміна колекції під час `foreach`

**Симптом:** `InvalidOperationException: Collection was modified; enumeration operation may not execute.`

```csharp
foreach (Animal pet in owner.Pets)
{
    if (pet is Cat)
        owner.Pets.Remove(pet);                // 💥
}
```

### Чому так

`foreach` за лаштунками використовує **перелічувач** (enumerator). Кожен `List<T>`
має внутрішній лічильник версії, який збільшується при кожній зміні. Перелічувач запам'ятовує
версію на старті й на кожному кроці порівнює. Версії розійшлися — виняток.

Захист потрібен, бо після `Remove` елементи зсуваються, і перелічувач би або
пропустив елемент, або вийшов за межі.

### Як виправити

**Варіант 1.** Ітерувати за індексом з кінця (видалення не ламає індекси ще не розглянутих елементів):

```csharp
for (int i = owner.Pets.Count - 1; i >= 0; i--)
{
    if (owner.Pets[i] is Cat)
        owner.Pets.RemoveAt(i);
}
```

**Варіант 2.** Перебирати **копію**, змінювати оригінал:

```csharp
foreach (Animal pet in new List<Animal>(owner.Pets))
{
    if (pet is Cat)
        owner.Pets.Remove(pet);
}
```

> Пізніше, коли будуть вивчені делегати, з'явиться ще один спосіб: `RemoveAll(...)`.

### Нюанс для `Dictionary`

У сучасному .NET (з Core 3.0) `Remove` і `Clear` під час перебору `Dictionary` виняток **не**
кидають, а `Add` та запис за новим ключем — кидають. У `List<T>` кидає будь-яка зміна.
Не покладайтеся на цю різницю; правило одне: не змінюйте колекцію, яку перебираєте.

## 9. Ключ без `Equals` і `GetHashCode`

**Симптом:** немає винятку — словник і множина **поводяться нелогічно**.

```csharp
Dog rex1 = new Dog { Id = 1, Name = "Рекс" };
Dog rex2 = new Dog { Id = 1, Name = "Рекс" };

var ages = new Dictionary<Dog, int>();
ages[rex1] = 3;
ages.ContainsKey(rex2);                        // False  ← очікували True

var set = new HashSet<Dog> { rex1, rex2 };
set.Count;                                     // 2      ← очікували 1
```

### Чому так

`Dictionary<TKey, …>` та `HashSet<T>` шукають елемент у два кроки:

1. обчислюють `GetHashCode()` і шукають «кошик»;
2. усередині кошика порівнюють ключі через `Equals`.

Якщо клас **не перевизначає** ці методи, діє успадкована від `object` реалізація:
**рівність за посиланням**. Два різні об'єкти `rex1` і `rex2` — це два різні посилання,
хоча дані в них однакові. Хеш-коди теж різні → словник навіть не заглядає в потрібний кошик.

### Як виправити (як зроблено в `Owner`)

```csharp
public class Owner : IEntity, IEquatable<Owner>
{
    public int Id { get; set; }

    public bool Equals(Owner? other) => other is not null && Id == other.Id;
    public override bool Equals(object? obj) => Equals(obj as Owner);
    public override int GetHashCode() => Id.GetHashCode();
}
```

Правила, які не можна порушувати:

1. Якщо `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()`. Зворотне не обов'язкове.
2. `GetHashCode` має використовувати тільки ті поля, що беруть участь у `Equals`.
3. Хеш не повинен змінюватися, поки об'єкт лежить у словнику.

### Обережно: змінний ключ

У `Owner` властивість `Id` має `set`. Якщо змінити `Id` вже після додавання в
`HashSet<Owner>`, хеш-код зміниться, а елемент залишиться лежати в «старому кошику» —
знайти його вже не вдасться. Найкращі ключі — **незмінні** (`init`, `record`, `readonly`).

### Альтернативи

- Ключем брати `Id` (`Dictionary<int, Dog>`) — найпростіше й найшвидше.
- Використовувати `record`: він генерує рівність за значеннями автоматично.
- `IEquatable<T>` реалізують ще й для того, щоб порівняння не потребувало boxing
  (особливо важливо для `struct`).

> **Висновок.** Використовуючи клас як ключ, спершу спитайте: «що для нього означає рівність?».

## 10. `List<Dog>` ≠ `List<Animal>`

**Символ:** `ERR_INVARIANT_LIST` · **Код:** `CS0029`

```csharp
List<Dog> dogs = new List<Dog>();
List<Animal> animals = dogs;                   // CS0029: Cannot implicitly convert type 'List<Dog>' to 'List<Animal>'
```

### Чому так

Припустимо, що це було б дозволено. Тоді:

```csharp
animals.Add(new Cat());                        // Cat — це Animal, тому "законно"
Dog first = dogs[0];                           // а це насправді кіт!
```

Список собак містив би кота. `List<T>` і **приймає** `T` (`Add`), і **віддає** його (`this[i]`),
тому безпечним є тільки точний збіг `T`. Така властивість називається **інваріантністю**.

### Як виправити

Якщо вам потрібно лише **читати**, використовуйте інтерфейс, який тільки віддає елементи:

```csharp
IEnumerable<Animal> readOnly = dogs;           // ок: IEnumerable<out T>
IReadOnlyList<Animal> list = dogs;             // ок: IReadOnlyList<out T>
```

Або зробіть копію: `new List<Animal>(dogs)`.

### Обмеження

Коваріантність працює **тільки для посилальних типів**. Для значущих — ні:

```csharp
IEnumerable<object> o = new List<int>();       // помилка (CS0266): int — значущий тип
```

> **Висновок.** «Кожен Dog — це Animal» не означає «набір Dog — це набір Animal».
> Це стає правдою лише тоді, коли набір **тільки віддає** елементи.

## 11. Порушення обмеження `where`

**Символ:** `ERR_CONSTRAINT` · **Коди:** `CS0311`, `CS0452`

```csharp
public class InMemoryRepository<T> where T : class, IEntity { … }

new InMemoryRepository<string>();              // CS0311
new InMemoryRepository<int>();                 // CS0452
```

### Чому так

Обмеження `where` — це **договір**: «підставляти можна лише типи, що вміють X». Це дозволяє
компілятору перевірити, що код усередині узагальненого класу використовує тільки доступні
можливості.

- `string` — це `class`, але **не реалізує** `IEntity` → `CS0311` (немає перетворення в `IEntity`).
- `int` — не `class` → `CS0452` («має бути посилальним типом»).

### Що можна вимагати

| Обмеження               | Значення                                                   |
|-------------------------|------------------------------------------------------------|
| `where T : class`       | посилальний тип                                            |
| `where T : struct`      | значущий тип (не `Nullable<>`)                             |
| `where T : new()`       | є публічний конструктор без параметрів                     |
| `where T : BaseClass`   | успадковується від `BaseClass`                             |
| `where T : IInterface`  | реалізує інтерфейс                                         |
| `where T : U`           | `T` походить від іншого параметра типу `U`                 |
| `where T : notnull`     | не `null` (для nullable-контексту)                         |
| `where T : unmanaged`   | значущий тип без посилань всередині                        |

### Правила запису

- `class` / `struct` / `notnull` / `unmanaged` — **першими**;
- `new()` — **останнім**;
- `class, struct` разом — не можна (`CS0449`);
- `where T : new(), class` → помилка `CS0401`.

Правильно: `where T : class, IEntity, new()`.

> **Висновок.** Обмеження — це не бюрократія, а спосіб **отримати доступ** до можливостей
> `T` (див. наступні пункти).

## 12. Доступ до члена `T` без обмеження

**Символ:** `ERR_NO_MEMBER` · **Код:** `CS1061`

```csharp
static string BrokenName<T>(T item)
{
    return item.Name;                          // CS1061: 'T' does not contain a definition for 'Name'
}
```

### Чому так

Для компілятора `T` без обмежень — це «будь-що», тому він знає лише про члени `object`
(`ToString`, `Equals`, `GetHashCode`, `GetType`). А `T` може виявитися будь-чим, наприклад `int`,
у якого властивості `Name` немає, тому звернення до `item.Name` компілятор не пропустить.

### Як виправити

```csharp
static string GetName<T>(T item) where T : Animal
{
    return item.Name;                          // тепер компілятор знає: T — це Animal
}
```

### Коли generic тут узагалі не потрібен

`GetName<T>(T item) where T : Animal` для **одного** параметра еквівалентний просто:

```csharp
static string GetName(Animal item) => item.Name;
```

Узагальнений варіант виправданий, якщо треба **зберегти точний тип** у результаті
(наприклад, метод повертає той самий `T`) або коли `T` використовується в кількох
місцях сигнатури. Інакше простіший звичайний метод.

### Чого робити не варто

Приводити «в лоб»: `((Animal)(object)item).Name` — це повертає перевірку типів на час
виконання і руйнує сенс generics.

## 13. `new T()` без `new()`

**Символ:** `ERR_NEW_T` · **Код:** `CS0304`

```csharp
static T BrokenCreate<T>()
{
    return new T();                            // CS0304: ... does not have the new() constraint
}
```

### Чому так

Компілятор не знає, чи має `T` публічний конструктор без параметрів. Замість `T` можуть
підставити `string` (у нього немає такого конструктора), абстрактний клас або інтерфейс.

### Як виправити

```csharp
static T Create<T>() where T : new()
{
    return new T();
}

Dog dog = Create<Dog>();                       // ок
```

### Підводні камені

- Обмеження `new()` вимагає **саме** конструктор без параметрів. Клас лише з `W(int x)` не
  підійде: виклик `Create<W>()` дасть `CS0310`.
- Передати аргументи конструктору через `where` не можна. Обхідні шляхи:
  `Activator.CreateInstance(typeof(T), args)` (ризик помилки вже на виконанні)
  або передача фабрики (це вже делегати — тема попереду).
- `new()` також не дозволяє абстрактні типи.

## 14. Компілятор не може вивести `T`

**Символ:** `ERR_INFERENCE` · **Код:** `CS0411`

```csharp
static T Create<T>() where T : new() => new T();

Animal a = Create();                           // CS0411: The type arguments ... cannot be inferred from the usage
```

### Чому так

**Виведення типу** (type inference) працює тільки за **аргументами** виклику. Тип, у який
ви присвоюєте результат (`Animal a = ...`), у виведенні **не бере участі**. У методі `Create<T>()`
параметрів немає, тому «джерел інформації» про `T` взагалі нема.

### Як виправити

```csharp
Animal a = Create<Dog>();                      // вказати аргумент типу явно
```

### Схожий випадок: суперечливі аргументи

```csharp
static T Max<T>(T a, T b) where T : IComparable<T> { … }

Max(3, "a");                                   // CS0411: T — це і int, і string?
```

Компілятор не знаходить єдиного `T`, який підходить обом. Виправлення — привести аргументи
до спільного типу або вказати `T` явно.

> **Висновок.** Якщо `T` не зустрічається в параметрах — його завжди треба вказувати вручну.

## 15. Оператори для `T`

**Символ:** `ERR_COMPARE` · **Код:** `CS0019`

```csharp
static T BrokenMax<T>(T a, T b)
{
    return a > b ? a : b;                      // CS0019: Operator '>' cannot be applied to operands of type 'T' and 'T'
}
```

### Чому так

Оператори `>`, `<`, `+` і подібні визначені для конкретних типів. Для довільного `T`
компілятор не може гарантувати, що оператор існує. Навіть `==` не працює для
`T` без обмежень (`CS0019`).

### Як виправити

**Спосіб 1 — через інтерфейс `IComparable<T>` (класичний):**

```csharp
static T Max<T>(T a, T b) where T : IComparable<T>
{
    return a.CompareTo(b) >= 0 ? a : b;
}

Max(3, 7);              // 7
Max("аб", "аа");        // "аб"
```

**Спосіб 2 — без обмежень, але з ризиком:**

```csharp
int r = Comparer<T>.Default.Compare(a, b);            // працює для будь-якого T…
```

Якщо `T` не реалізує `IComparable`, це впаде на виконанні:
`ArgumentException: At least one object must implement IComparable`.

**Спосіб 3 — сучасний (C# 11+, generic math):**

```csharp
using System.Numerics;

static T Max<T>(T a, T b) where T : IComparisonOperators<T, T, bool>
{
    return a > b ? a : b;                             // оператор дозволено обмеженням
}
```

Так можна вимагати навіть арифметику (`INumber<T>`). Це тема блоку 6 у `Ідеї прикладів.txt`.

### Обережно з `CompareTo(null)`

`a.CompareTo(b)` для посилального типу впаде з `NullReferenceException`, якщо `a == null`.

## 16. Неправильне оголошення `in`/`out`

**Символ:** `ERR_VARIANCE_DECL` · **Код:** `CS1961`

```csharp
interface IBadProducer<out T>
{
    T Get();                                   // ок: T на виході
    void Set(T value);                         // CS1961: Invalid variance ... 'T' is covariant
}
```

### Чому так

- `out T` означає: «`T` лише **виходить** з інтерфейсу» (результат методу, `get`-властивість).
  Тому `IProducer<Dog>` можна вважати `IProducer<Animal>`.
- `in T` означає: «`T` лише **входить** до інтерфейсу» (параметр методу).
  Тому `IConsumer<Animal>` можна вважати `IConsumer<Dog>`.

Метод `Set(T value)` приймає `T`. Якби `IBadProducer<Dog>` мав право
виглядати як `IBadProducer<Animal>`, у нього можна було б записати `Cat`.
Компілятор такий інтерфейс просто забороняє.

### Правила

- `in`/`out` дозволені **тільки для інтерфейсів і делегатів**, не для класів і структур.
- Параметри `ref` та `out` (у методах) вважаються і входом, і виходом → інваріантність.
- Variance діє лише для **посилальних** аргументів типу.

### Як виправити: розділити інтерфейс

Саме так зроблено в проєкті:

```csharp
public interface IReadOnlyRepository<out T> where T : class, IEntity   // лише віддає T
{
    T? FindById(int id);
    IEnumerable<T> GetAll();
}

public interface IRepository<T> : IReadOnlyRepository<T> where T : class, IEntity   // ще й приймає
{
    void Add(T entity);
    bool Remove(int id);
}
```

Приклади зі стандартної бібліотеки: `IEnumerable<out T>`, `IReadOnlyList<out T>` (коваріантні);
`IComparer<in T>`, `IEqualityComparer<in T>` (контраваріантні); а от `List<T>`, `IList<T>`,
`ICollection<T>` — інваріантні (і читають, і пишуть).

## 17. Контраваріантність працює лише в один бік

**Символ:** `ERR_VARIANCE_DIRECTION` · **Код:** `CS0266`

```csharp
IValidator<Animal> animalValidator = new AnimalValidator();
IValidator<Dog> asDogValidator = animalValidator;        // ✅ ок

IValidator<Dog> dogValidator = new DogValidator();
IValidator<Animal> broken = dogValidator;                // ❌ CS0266
```

### Чому так

Інтерфейс `IValidator<in T>` **споживає** `T`. Логіка проста:

- Валідатор для **будь-якої** тварини вміє перевірити й собаку → його можна
  використати там, де потрібен валідатор собак. ✅
- Валідатор для **собак** читає `item.Breed`, якого немає в `Cat`. Дати йому кота
  — значить попросити його зробити неможливе. ❌

Запам'ятовується так:

> **Споживач загальнішого типу може замінити споживача конкретнішого. Виробник конкретнішого
> типу може замінити виробника загальнішого.**

### «Explicit conversion exists»

Повідомлення каже, що явне приведення теоретично існує. Так, `(IValidator<Animal>)dogValidator`
скомпілюється, але під час виконання впаде з `InvalidCastException`, бо об'єкт `DogValidator`
реалізує лише `IValidator<Dog>`. Тобто «прибрати» помилку кастом означає **перенести її на виконання** —
саме те, чого ми хотіли уникнути.

## 18. `IRepository<Dog>` ≠ `IRepository<Animal>`

**Символ:** `ERR_REPO_INVARIANT` · **Код:** `CS1503`

```csharp
static void FillWithCats(IRepository<Animal> repo)
{
    repo.Add(new Cat { Id = 99, Name = "Підкинутий кіт" });
}

var dogRepo = new InMemoryRepository<Dog>();
FillWithCats(dogRepo);                                   // CS1503: cannot convert 'InMemoryRepository<Dog>' to 'IRepository<Animal>'
```

### Чому так

Метод `FillWithCats` **записує** тварину. Якби йому дозволили передати
сховище собак, у нього опинився б кіт. `IRepository<T>` має `Add(T)`, тому інваріантний — і компілятор
це чесно виконує (див. також [пункт 16](#16-неправильне-оголошення-inout)).

### Як виправити

**Для читання** — приймайте коваріантний інтерфейс:

```csharp
static void PrintAll(IReadOnlyRepository<Animal> repo)      // ✅ dogRepo підходить
{
    foreach (Animal animal in repo.GetAll())
        Console.WriteLine(animal);
}
```

**Для запису** — узагальнюйте метод, тоді `T` збігається з типом сховища:

```csharp
static void AddOne<T>(IRepository<T> repo, T item) where T : class, IEntity
{
    repo.Add(item);                                         // T = Dog → item мусить бути Dog
}
```

Тут `Cat` у `IRepository<Dog>` покласти неможливо — саме на цьому й наполягає інваріантність.

> **Висновок.** Розділення інтерфейсів на «тільки читання» та «читання-запис» — це і
> хороший дизайн (принцип розділення інтерфейсів), і спосіб отримати безпечну коваріантність.

# Шпаргалки

## Шпаргалка: variance

| Позиція `T`               | Слово | Назва            | Приклад               | Правило                                        |
|---------------------------|-------|------------------|-----------------------|------------------------------------------------|
| лише результат (виробник) | `out` | коваріантність   | `IEnumerable<out T>`  | `Producer<Dog>` → `Producer<Animal>`           |
| лише параметр (споживач)  | `in`  | контраваріантність | `IComparer<in T>`   | `Consumer<Animal>` → `Consumer<Dog>`           |
| і те, й те                | —     | інваріантність   | `List<T>`, `IList<T>` | точний збіг типів                              |

Перевірочні питання:

1. «Чи є в цьому інтерфейсі метод, що **приймає** `T`?» → `out` заборонено.
2. «Чи є метод, що **повертає** `T`?» → `in` заборонено.
3. «Чи `T` — посилальний тип?» → для значущих variance не діє.
4. «Це інтерфейс або делегат?» → для класів і структур variance немає.

## Шпаргалка: обмеження `where`

| Що потрібно всередині generic-коду | Обмеження                  |
|------------------------------------|----------------------------|
| повертати/порівнювати з `null`     | `where T : class`          |
| працювати з `T?` як з `Nullable<T>`| `where T : struct`         |
| створювати `new T()`               | `where T : new()`          |
| викликати члени класу              | `where T : BaseClass`      |
| викликати члени інтерфейсу         | `where T : IInterface`     |
| порівнювати `a.CompareTo(b)`       | `where T : IComparable<T>` |
| оператори `>`, `+`                 | `where T : IComparisonOperators<…>` / `INumber<T>` |

## Швидка діагностика за кодом помилки

| Код       | Про що                                                            | Пункт |
|-----------|-------------------------------------------------------------------|-------|
| `CS0019`  | оператор не застосовний до `T`                                    | 15    |
| `CS0029`  | немає неявного перетворення (`List<Dog>` → `List<Animal>`)         | 10    |
| `CS0266`  | потрібне явне перетворення (variance у зворотний бік)              | 17    |
| `CS0304`  | `new T()` без `new()`                                              | 13    |
| `CS0310`  | у типу немає публічного конструктора без параметрів                | 13    |
| `CS0311`  | тип не відповідає обмеженню (немає перетворення)                   | 11    |
| `CS0401`  | `new()` має бути останнім в обмеженнях                             | 11    |
| `CS0411`  | неможливо вивести аргументи типу                                   | 14    |
| `CS0449`  | `class`/`struct`/… поєднано неправильно                            | 11    |
| `CS0452`  | потрібен посилальний тип, передано значущий                        | 11    |
| `CS1061`  | у `T` немає такого члена                                           | 12    |
| `CS1503`  | аргумент не перетворюється в тип параметра                         | 2, 18 |
| `CS1961`  | неправильне розташування `in`/`out`                                | 16    |
| `CS8602`  | розіменування можливого `null`                                     | 4     |
| `CS8629`  | `Nullable<T>` може бути `null`                                     | 5     |

## Словник термінів

| Термін                         | Пояснення                                                                    |
|--------------------------------|------------------------------------------------------------------------------|
| **Відкритий тип**              | `List<>` / `EntityCounter<T>` — шаблон з незаповненим `T`                    |
| **Закритий тип**               | `List<Dog>` — `T` підставлено; це окремий повноцінний тип                    |
| **Аргумент типу**              | конкретний тип, підставлений замість `T` (`Dog` у `List<Dog>`)               |
| **Обмеження (constraint)**     | умова `where`, що звужує допустимі аргументи типу                            |
| **Boxing / unboxing**          | упакування значущого типу в `object` і розпакування назад                    |
| **Інваріантність**             | `Foo<Dog>` і `Foo<Animal>` не пов'язані                                      |
| **Коваріантність (`out`)**     | `Foo<Dog>` можна використовувати як `Foo<Animal>`                            |
| **Контраваріантність (`in`)**  | `Foo<Animal>` можна використовувати як `Foo<Dog>`                            |
| **Виведення типу**             | автоматичний вибір `T` компілятором за аргументами виклику                   |
| **Перелічувач (enumerator)**   | об'єкт, що обслуговує `foreach` (`IEnumerator<T>`)                           |

## Загальні правила, що випливають з усього розбору

1. **Віддавайте перевагу помилкам компіляції над помилками виконання.** Саме для цього
   існують generics (пункти 1–3 проти 10–18).
2. **Інтерфейс «тільки читання» можна робити коваріантним; «читання-запис» — ні.**
3. **Не приглушуйте попередження** про `null` (`!`) і `Nullable` без перевірки.
4. **`Foo<A>` і `Foo<B>` — різні типи**; не очікуйте спільної статики.
5. **Для ключів словників і множин визначайте рівність** (`IEquatable<T>`, `GetHashCode`) або
   беріть незмінні прості ключі (`Id`).
6. **Не змінюйте колекцію, яку перебираєте** у `foreach`.
7. **Обмеження `where` — інструмент**, який відкриває `T` нові можливості; підбирайте
   мінімально достатнє.
8. Якщо `T` в методі не використовується ніде, крім одного параметра, спитайте себе,
   чи потрібен тут generic.
